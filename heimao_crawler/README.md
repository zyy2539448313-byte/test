# 黑猫投诉公开数据采集脚本

配套《执行手册_工具与30天节奏》第 1 周交付物 ①。用途：为「上门维修透明化」项目持续积累黑猫投诉公开数据（防水补漏 / 管道疏通 / 空调维修等品类），供价格库校准、选题素材、竞品监控分析使用。

## 一、快速开始

```bash
pip install -r requirements.txt

# 1) 抓一轮最新投诉流（自动按关键词过滤 + 去重，约 50 页 500 条上限）
python heimao.py latest --pages 50

# 2) 查竞品商家投诉量（啄木鸟/万师傅/鲁班到家…）
python heimao.py merchant 啄木鸟 万师傅 鲁班到家 极客修

# 3) 对命中记录抓详情页全文（默认更慢的间隔）
python heimao.py detail --input data/complaints.jsonl --limit 20

# 4) 长期增量：每 30 分钟自动抓一轮（也可交给 WorkBuddy 定时任务）
python heimao.py poll --interval 30
```

产物（全部在 `data/`，已 gitignore，不入版本库）：

| 文件 | 内容 |
|---|---|
| `complaints.jsonl` | 命中的投诉记录（sn、标题、商家、诉求、问题、摘要、时间、链接等） |
| `complaints.csv` | 同上，Excel 可直接打开（utf-8-sig） |
| `details.jsonl` | 详情页全文：投诉对象/问题/要求/涉诉金额/进度/正文/时间线 |
| `merchants_*.csv` | 商家检索结果（uid、近 30 天投诉量），竞品监控名单 |
| `seen_sns.txt` / `seen_detail.txt` | 去重状态，删掉即全量重抓 |

## 二、数据从哪来（2026-10 实测）

脚本**只**访问以下匿名状态下公开的来源：

1. **最新投诉流** `GET /api/index/feed` —— 全站最新投诉，每页固定 10 条，匿名最多翻 50 页（约最新 500 条，大致覆盖最近几十分钟）。脚本做客户端关键词过滤。要积累样本量，靠 `poll` 模式滚动抓，而不是一次翻几百页。
2. **商家检索** `GET /api/company/search`、`/api/company/main_search` —— 按名称查商家 uid、近 30 天投诉量。
3. **投诉详情页** `GET /complaint/view/{sn}/?sld=xxx` —— 公开 SSR 页面（sld 参数由 feed 返回的 url 自带）。

## 三、反爬说明（平台的防线 vs 脚本的策略）

### 平台当前的防线（实测）

| 防线 | 表现 |
|---|---|
| 登录墙 | 关键词搜索页整体跳转微博登录；`index/s` 接口返回 10005；feed 翻页 >50 页返回 10017 |
| 接口签名 | 商家投诉列表等接口要求 `ts+rs+md5签名`，且服务端对匿名请求一律 10005 |
| 风控 SDK | 登录页加载网易易盾 + 微博指纹检测（wbBotDetector） |
| 频控 | 高频访问返回 429/403 |

### 脚本的策略：不硬闯

- **只走仍然公开的接口**。被关闭的（关键词搜索、商家投诉列表）一律不碰，不做签名爆破、不用他人账号或 Cookie 绕过登录——那一步跨过去就是违规爬取，性质完全不同。
- **低速**：默认每次请求间隔 1.5s + 0~1.5s 随机抖动（详情页 2s+），比人工浏览还慢。
- **限量**：单轮 feed 最多 50 页 500 条；详情页建议 `--limit` 分批。
- **失败即停**：遇到 10017（登录墙）、10005（风控码）、429/403 立即停止本轮并提示等待，绝不自动重试硬顶。
- **UA 轮换**：仅为避免被简单 UA 黑名单误伤，不代表可以突破任何访问控制。
- **指数退避**：网络错误/5xx 最多重试 3 次，间隔 5s/10s/20s。

如果未来 feed 接口也关闭匿名访问：**停手**。届时建议改为人工导出或寻找官方合作渠道，不要再升级对抗手段。

## 四、合规注意（务必读完再用）

1. **robots 协议**：`tousu.sina.com.cn/robots.txt` 不存在（返回 404 提示页），即平台未通过 robots 声明抓取规则。这不等于授权，所以脚本自我施加上述频率与范围限制。
2. **数据用途**：仅用于内部商业分析（价格库校准、选题、竞品研究）。黑猫详情页明确声明「未经授权，本平台案例禁止任何转载」——**不要把投诉原文二次发布**到任何公开渠道（包括我们自己的内容账号），对外只能用聚合统计结论（如"近 30 天防水补漏类投诉 X 条，中位报价 Y 元"）。
3. **个人信息保护**：投诉人昵称默认打码（`正*喵`），正文中的手机号自动掩码；数据文件已 gitignore 不入库、不上传云端。分析完成后建议定期清理原始文件（《个人信息保护法》最小必要原则）。
4. **不干扰平台**：低频访问不影响对方系统正常运行是底线，也是《数据安全法》和既有司法判例（如微博诉脉脉案、大众点评诉百度案）划的红线之一。
5. **账号红线**：不要为了让脚本"更好用"而传入登录 Cookie 或账号——需要登录才能拿的数据，说明平台不想让你以这种方式拿。

## 五、接入 30 天节奏的建议

- **第 1 周**：跑一次 `latest --pages 50` + `merchant` 拿到基线；把 `poll --interval 30` 挂起来（或设 WorkBuddy 定时任务），一周可积累数千条滚动样本，筛出维修类几百条，满足"500 条样本"目标。
- **第 2 周**：对命中记录跑 `detail`，把涉诉金额、投诉问题字段灌进飞书多维表格做价格校准参考。
- **每周复盘**：`merchant` 监控啄木鸟等竞品投诉量变化，作为选题与热点素材。
